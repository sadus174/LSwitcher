# Design

## Context

Мотивация и границы описаны в proposal.md. Сейчас AppDelegate создаёт статическое меню и всегда вызывает showSettings при запуске. AppModel объединяет настройки и проверку готовности раз в секунду; tooltip при любой неготовности предлагает проверить разрешения. Исключения приложений добавляются через NSOpenPanel. KeyboardEngine хранит одну пятисекундную CorrectionUndo, а PersonalWords нормализует список до 5000 слов. Выбор цели ввода уже учитывает глобальный AX-фокус; этот механизм сохраняется.

Сборка scripts/build-dmg.sh уже подписывает вложенный updater и приложение при SIGN_IDENTITY и отправляет DMG на нотариализацию при NOTARY_PROFILE. При этом отдельный путь ZIP обновления требует проверки. Updater проверяет подписи codesign и подписанный манифест; изменение доверительной модели не должно ослаблять закреплённый ключ Ed25519.

## Goals / Non-Goals

**Goals:** повторно использовать существующие настройки и механизмы ввода, ограничить новое состояние, обновлять интерфейс без тяжёлых AX-запросов в callback клавиатуры, отделить подготовку доверенного выпуска от наличия сертификатов.

**Non-Goals:** менять словарь или алгоритм выбора замен, переделывать Spotlight, вводить стороннюю службу автозапуска, регистрировать login item во время тестов ядра, отправлять ввод в существующие удалённые сессии.

## Decisions

### 1. Меню и снимок приложения

Через NSMenuDelegate обновлять динамические пункты при открытии. Хранить снимок bundle ID, PID и отображаемого имени выбранной цели. Использовать существующий AccessibilityFocus.keyboardApplication вне event-tap callback; при невозможности разрешить цель не выбирать случайное приложение. При исполнении проверять, что снимок ещё относится к живому процессу. Изменение исключений выполнять через общий метод AppModel, который используют и настройки.

Альтернатива — определять frontmostApplication при нажатии — может менять цель после открытия настроек или меню. Снимок даёт предсказуемую связь текста пункта с действием. Защита менеджеров паролей и Secure Input остаётся независимой от пользовательского списка.

### 2. Единая модель текущего состояния

Ввести небольшой тип OperationStatus и чистый выбор причины по снимку входных данных; разместить проверяемую логику в LSwitcherCore. Источники — enabled/automatic, разрешения, sessionSuspended, Secure Input, состояние обработчика и доступный контекст цели. Приоритет соответствует specs/operation-status/spec.md. Текущий статус и последнее действие KeyboardEngine — разные свойства.

Обновлять снимок существующим health timer, событиями смены приложения/настроек и открытием меню. Проверки поля выполнять вне callback ввода с действующими ограничениями времени; не читать текст ради статуса. Если доступность не определена, показывать это явно. Альтернатива — собирать причины в каждой View — создаёт рассогласование. Новый частый таймер для статусов не нужен.

### 3. Кандидат личного исключения после отмены

Отделить пятисекундную возможность отмены от нового UndoExclusionCandidate. После принятой отмены хранить original, идентификатор приложения, монотонное время создания и идентификатор кандидата. Кандидат один, до 80 символов, срок — 60 секунд. События очистки перечислены в спецификации; закрытие/открытие меню их не имитирует. При переключении фокуса на интерфейс самого LSwitcher не считать это переходом к другому целевому приложению.

Проверять срок и идентификатор повторно при нажатии, чтобы открытое меню не сохраняло устаревшее слово. Очистку обеспечивать health timer и жизненным циклом; в меню выводить только однострочное безопасное представление. Сохранение через AppModel возвращает явный результат: добавлено, уже есть, неверное слово, лимит. Проверять вместимость до записи: существующий prefix(5000) не должен молча терять старые слова. Кандидат не передавать в diagnostic.

Альтернатива — автоматически обучаться на каждом Backspace — сохраняет случайные отмены и не соответствует явному действию пользователя. Постоянная история отмен не нужна.

### 4. Автозапуск через macOS

Использовать SMAppService.mainApp с register/unregister и системным status. Не дублировать статус булевым флагом UserDefaults. Обработать enabled, notRegistered, requiresApproval, notFound и неизвестные значения; требование подтверждения не считать успехом. Для перехода использовать системный openSystemSettingsLoginItems.

Источник запуска определять по событию kAEOpenApplication с keyAELaunchedAsLogInItem до решения об открытии настроек. Обычный запуск и applicationShouldHandleReopen сохраняют окно настроек. Проверить передачу reopen существующему экземпляру: текущая блокировка второго процесса не должна поглощать стандартное повторное открытие.

Альтернатива — собственный LaunchAgent или отдельный helper — добавляет ненужное обслуживание. Системные API и признак login launch подтверждены [Apple ServiceManagement](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29) и [Apple launch event](https://developer.apple.com/documentation/coreservices/1556410-launch_apple_event_constants/keyaelaunchedasloginitem).

### 5. Завершение существующего процесса подписи

Расширить локальные инструменты выпуска, сохранив поддержку ad-hoc сборки для разработки. Для режима доверенного выпуска сделать предварительную проверку Developer ID и профиля без чтения закрытых ключей. Подписать updater до приложения, использовать hardened runtime и timestamp, проверить готовую подпись. Нотариализовать приложение через поддерживаемый архив, прикрепить билет к .app, затем изготовить финальный ZIP обновления и его подписанный манифест. Финальные хеши вычислять после всех изменений артефакта. Отдельно подготовить и проверить DMG с билетом. Проверить Gatekeeper на реально распространяемых копиях.

Альтернатива — нотариализовать только DMG — не подтверждает готовность .app в ZIP встроенного обновления. Отсутствие доступа Apple фиксируется как внешняя зависимость: локальные функции и проверки не блокируются, доверенный выпуск не считается готовым. Служебные scripts сейчас игнорируются Git; при изменении процесса выпуска включать в версионирование только необходимые обезличенные скрипты, без keys, корпусов и временных файлов.

## Risks / Trade-offs

- Смена фокуса из-за самого меню → отдельный снимок целевого приложения и проверка перед действием; не использовать последнее приложение как безусловный fallback.
- Длительные AX-запросы → существующие timeout, отсутствие AX-вызовов в callback ради меню/статусов.
- Слово остаётся в открытом меню после истечения срока → инвалидировать пункт и повторно проверять кандидата на нажатии; не сохранять текст в долгоживущих closure.
- Отличия login launch и обычного reopen → проверка Apple event и реального входа в систему; программная имитация не заменяет её.
- Новая подпись меняет поведение разрешений → отдельная проверка перехода с ad-hoc и явная инструкция по фактическому результату.
- Физический сон, выход из системы и проверка минимальной macOS могут требовать отдельного тестового сеанса → пометить непроверенные сценарии, не выдавать smoke-тест за их подтверждение.

## Migration Plan

1. Сохранять существующие ключи настроек и форматы исключений. Новое временное состояние не мигрируется.
2. Выполнять этапы: меню и статусы → слово после отмены → автозапуск → совместимость → доверенный выпуск.
3. Проверить release-сборку, LSwitcherChecks и встроенные smoke-тесты на изолированных документах. После тестов восстановить настройки; для автозапуска восстановить системную регистрацию.
4. Реальные проверки сна/входа выполнять в подходящем тестовом сеансе, без прерывания текущей работы пользователя неожиданным выходом из системы. Termius проверять в отдельном безопасном окружении без отправки команд в существующую сессию.
5. При откате не оставлять login item, указывающий на временную сборку. Встроенный updater сохраняет предыдущую копию; необратимых миграций данных нет.
6. Обновить README и TEST-REPORT, отдельно отразить подтверждение пользователя по Spotlight. Публикацию выполнять отдельным действием после проверки артефактов.
